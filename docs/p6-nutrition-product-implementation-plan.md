# P6 영양 콘텐츠·제품 추천 구현 계획

## 목표

기존 영양 콘텐츠 API를 명세에 맞게 완성하고, 사용자가 등록한 영양소 목표와 세 VIVEGEN 제품의 표시 기능정보를 백엔드에서 결정적으로 매칭해 챗봇 컨텍스트에 주입한다.

## Task 1 — 스키마와 카탈로그

**상태: 완료**

- Flyway V10으로 기존 `nutrition_contents` 필드를 보강한다.
- `nutrition_products`, `nutrition_product_functions`, `user_nutrient_needs`를 생성한다.
- 세 제품과 제공받은 기능정보를 정적 카탈로그로 적재한다.
- MySQL 통합 테스트로 FK, 고유키, 제품·기능 개수를 검증한다.

## Task 2 — 영양소 목표와 제품 매칭

**상태: 완료**

- 지원 영양소 코드를 enum으로 제한한다.
- 목표 전체 교체·조회·삭제 서비스를 구현한다.
- 제품별 매칭 영양소 수를 계산하고 0건 제품은 제외한다.
- 같은 점수는 제품 ID 순으로 정렬한다.
- 증상이나 자유문장에서 영양소를 추론하는 로직은 만들지 않는다.

## Task 3 — 영양 콘텐츠·즐겨찾기 API

**상태: 완료**

- 목록 필터, 상세, 즐겨찾기 추가·해제, 내 즐겨찾기 페이징을 구현한다.
- `timingTag` 미지정 시 현재 근무와 시각으로 태그를 결정한다.
- 입력 enum, 페이지 범위, 중복·미존재·소유권 오류를 명세 상태코드로 매핑한다.

## Task 4 — 제품·영양소 API

**상태: 완료**

- 영양소 목표 PUT/GET/DELETE를 구현한다.
- 제품 카탈로그와 내 추천 결과 GET을 구현한다.
- 응답에 매칭 영양소, 제공된 기능정보, 건강기능식품 고지문을 포함한다.

## Task 5 — 챗봇 컨텍스트와 프롬프트

**상태: 완료**

- `ChatContextSnapshot`에 영양소 목표와 백엔드 추천 후보를 추가한다.
- NUTRITION 근거 발췌에 진단 금지·표시 문구 한정·복용량 생성 금지를 추가한다.
- 모델은 제품 후보를 계산하지 않고 주어진 후보의 선택 이유만 설명한다.
- 의료·응급 분기에서는 제품 추천을 반환하지 않는다.

## Task 6 — 검증과 배포

**상태: 완료**

- 단위·MVC·MySQL 통합·전체 회귀 테스트를 실행한다.
- Docker에서 V10 적용, 콘텐츠 조회, 목표 저장, 추천 조회, 챗봇 안전 경로를 확인한다.
- `docs/superpowers`와 AI 기여자 메타데이터가 없음을 감사한다.
- 기능 단위로 커밋하고 `p6`에 푸시한다.

## 운영 전 확인사항

- 제품 기능정보는 제공받은 문구로 적재했다. 출시 전 실제 제품 라벨, 기능성 원료 인정 내용, 섭취 시 주의사항 및 광고심의 결과와 대조한다.
- 건강기능식품을 질병 예방·치료 또는 의약품으로 오인하게 하는 표현은 사용하지 않는다.
- 참고: [식품 등의 표시·광고에 관한 법률 제8조](https://www.law.go.kr/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1030102807), [건강기능식품의 표시기준](https://www.law.go.kr/LSW/admRulInfoP.do?admRulSeq=2100000213790&chrClsCd=010201)

## 검증 결과

- Gradle 전체 테스트 통과
- MySQL Testcontainers에서 제품 3건, 기능정보 26건, 사용자 영양소 목표 FK 저장 확인
- 기존 Docker 볼륨에서 Flyway V10·V11 순차 적용 확인
- 실제 API로 제품 조회, 목표 저장, 추천 정렬, 콘텐츠 페이징, 즐겨찾기 생성·조회·삭제 확인
- 검증용 사용자 목표와 즐겨찾기 데이터 삭제 후 추천 0건 확인
